版本目的 / 需求背景

运营侧计划在双十一投放「特惠包阶梯复购」与「金币充值加赠」。加赠可走现有「赠送多少币」配置；复购依赖「买过 A 才看到 B」与「每人限购 N 次」，当前产品管理不具备这两项能力，也无法按时间窗自动控制商品对 APP 的可见性（仅有手动「产品状态」与「折扣过期时间」，折扣过期只影响折扣价，不控制商品上下架）。

本期把限购数、前置条件、有效时间做成可复用的商品级长期能力，APP 金币充值页继续由后端返回可购列表驱动展示，前端页面不改版、不加复购弹窗、不做邀请裂变。

V51-PROD-01

商品限购数

适用范围：财务管理 → 产品管理 → 「添加」「修改」信息弹窗。

功能逻辑

为每个商品增加「限购数」配置。表示单个用户对该商品允许累计「支付成功」的次数上限。达到上限后，该商品对该用户不再出现在可购列表中，下单接口也拒绝再次购买。

未配置限购（空或 0）时，不限制购买次数。限购与前置条件、有效时间独立计算，最终是否可购取交集（见 V51-API-01 与组合场景）。

业务规则

  • 字段名：「限购数」。
  • 类型：非负整数；输入框允许清空。
  • 默认：空。空或 0 均表示「不限购」。
  • 填写 ≥ 1 时生效：用户对该商品「支付成功」订单数 ≥ 限购数后，视为已达上限。
  • 计数口径：仅统计支付成功订单。未支付、取消、失败不计。
  • 退款：不回退限购次数。即成功支付后发生退款，仍计入已购次数，不恢复可购名额。
  • 历史订单：能力上线后，按该用户对该商品历史支付成功次数累计；不因配置晚于首单而忽略已有成功单。

页面交互

  • 位置：添加 / 修改弹窗内，与前置条件、有效时间集中在「产品状态」附近的新增配置区（见 Demo）。
  • 控件：数字输入；旁注文案「0 或不填表示不限购」。
  • 点「确定」：与其它字段一并提交保存；成功关闭弹窗并刷新列表（与现网一致）。
  • 点「取消」或关弹窗：不保存本次编辑（与现网一致）。

异常

  • 输入非整数、负数、小数：不提交；Toast「限购数须为大于等于 0 的整数」；弹窗不关，已填内容保留。
  • 保存接口失败：Toast「保存失败，请稍后重试」；弹窗不关。

数据流转

运营在弹窗填写限购数 → 保存写入商品配置 → 列表展示该值 → APP 列表 / 下单接口读取配置，并结合该用户支付成功次数判断是否仍可购。

V51-PROD-02

商品前置条件

适用范围：同上添加 / 修改弹窗。用于配置「满足某条件后才展示并可购买本商品」，支撑特惠包复购链路。

功能逻辑

前置条件拆成两个字段：行为类型、关联商品。本期行为类型只上线「购买过」。当行为与商品均配置时，仅当该用户对关联商品存在至少一笔支付成功订单，本商品才对该用户可见可购。

前置条件默认为空：不启用前置，商品是否可购只受上架态、有效时间、限购、可行类型等其它规则约束。

业务规则

1. 字段与默认（成组、先后关系）

  • 后台将「前置条件」作为一组配置：先选「前置行为」，再出现该行为对应的第 2 步对象控件。
  • 「前置行为」：枚举；默认空（不启用）。本期可选值仅：「购买过」。枚举可扩展。
  • 当行为 =「购买过」：第 2 步展示「前置商品」，必填，单选一个商品。
  • 当行为为空：不展示第 2 步，无前置条件。
  • 当行为为其它未来类型：第 2 步不是「前置商品」，而是该行为对应的对象控件（本期不上线其它行为）。
  • 行为为「购买过」但未选商品：校验失败，不允许保存。

2. 「购买过」判定

  • 用户对「前置商品」存在 ≥ 1 笔支付成功订单，即满足。
  • 不要求前置商品仍在有效期内或仍上架；历史成功单即可。
  • 不考虑后续退款：一旦曾支付成功，永久视为已购买过该前置商品（用于前置判定）。
  • 未支付、取消、失败订单不满足「购买过」。

3. 商品选择器

  • 必须展示商品 ID，并同时展示名称；建议附带类型、推广价或价格，便于运营辨认。
  • 仅允许选择一个前置商品。
  • 不可选择当前正在编辑的商品自身。
  • 可选范围：产品管理中已有商品（含下架商品，便于配历史依赖）；若关联商品后来被删除，见异常。
  • 支持按名称或 ID 搜索后选择。

页面交互

  • 位置：限购数下方，整组「前置条件」红区展示（见 Demo）。
  • 第 1 步选「不启用」：第 2 步隐藏，仅提示无需配置对象。
  • 第 1 步选「购买过」：立刻展示第 2 步「前置商品」选择器，可搜索并单选。
  • 从「购买过」改回「不启用」：清空已选前置商品，并隐藏第 2 步。
  • 已选前置商品：展示为「ID · 名称 · 价格」；可重选。
  • 保存、取消行为与现网弹窗一致。

异常

  • 行为已选但未选商品：Toast「请选择前置商品」；不关闭弹窗。
  • 选择自身：选择器内不可选；若异常提交，Toast「前置商品不能是当前商品」。
  • 关联商品已被删除：后台打开修改时展示「商品已删除（原 ID：x）」；保存前须重选或清空前置；APP 侧对该商品按「前置不满足」处理，直至运营修正配置。
  • 保存失败：Toast「保存失败，请稍后重试」。

数据流转

弹窗写入前置行为枚举值 + 前置商品 ID → 持久化到商品配置 → 列表展示可读摘要 → APP 列表 / 下单按用户订单记录判定是否满足「购买过」。

V51-PROD-03

商品有效时间与当前状态

适用范围：添加 / 修改弹窗 + 列表「当前状态」展示。解决双十一特惠包仅当天可售等需求；作为长期定时能力保留。

功能逻辑

为商品增加有效时间窗（开始、结束）。APP 是否可售，在「产品状态为上架」的前提下，还须落在有效时间窗内（若配置了时间）。后台列表用「当前状态」把「手动产品状态 + 时间窗」汇总成运营可读结果。

「折扣过期时间」继续只服务折扣 / 推广价逻辑，不承担商品上下架。产品状态为下架 / 未上架时，无论是否在时间窗内，APP 均不可售。

业务规则

1. 字段

  • 「有效开始时间」：日期时间，可空。
  • 「有效结束时间」：日期时间，可空。
  • 都为空：不限制时间窗；可售只看产品状态等其它条件。
  • 仅开始：当前时间 ≥ 开始，才进入时间窗。
  • 仅结束：当前时间 ≤ 结束，才在时间窗内。
  • 开始与结束都填：开始 ≤ 当前 ≤ 结束为窗内；若开始 > 结束，保存时校验失败。
  • 时区：与现网后台 / 服务器统一时区；PRD 验收按服务器时间。

2. 当前状态

  • 产品状态为「未上架」或「下架」：当前状态与产品状态文案一致。
  • 产品状态为「上架」且未配置有效时间：当前状态「上架」。
  • 产品状态为「上架」且未到开始时间：当前状态「未开始」。
  • 产品状态为「上架」且在时间窗内：当前状态「售卖中」。
  • 产品状态为「上架」且已过结束时间：当前状态「已结束」。
  • 「未开始」「已结束」时 APP 不可见不可购，即使产品状态仍为上架。

3. 与产品状态的关系

  • 到点 / 过期：不自动改写「产品状态」字段；仅「当前状态」与 APP 可售结果变化。
  • 运营可随时手动下架，立即对 APP 不可售。

页面交互

  • 弹窗新增两个日期时间控件；可清空。
  • 列表「当前状态」随列表刷新按服务器当前时间计算；不要求秒级倒计时。

异常

  • 开始晚于结束：Toast「有效开始时间不能晚于结束时间」；不保存。
  • 时间格式非法：Toast「请填写正确的有效时间」；不保存。
  • 保存失败：Toast「保存失败，请稍后重试」。

数据流转

弹窗保存有效开始 / 结束 → 写入商品配置 → 列表计算当前状态 → APP 列表 / 下单在上架前提下再判断时间窗。

V51-PROD-04

产品管理列表字段

适用范围：财务管理 → 产品管理列表。

功能逻辑

运营在列表即可看到限购、前置、有效时间与汇总后的当前状态，减少每次点开修改才能确认活动商品是否配错、是否已过期。

业务规则

  • 「限购数」列：不限购展示「不限」；有限购展示数字 N。
  • 「前置条件」列：无前置展示「—」；有则展示「购买过 · {商品ID} · {商品名称}」。
  • 「有效时间」列：都未配置展示「不限」；否则展示「开始 ~ 结束」，缺一侧用「—」占位。
  • 「当前状态」列：未上架 / 下架 / 上架 / 未开始 / 售卖中 / 已结束。
  • 原有列（ID、名称、价格、权益、排序、卡型、更新时间、操作等）保留。
  • 筛选：本期不强制新增「按当前状态筛选」；非验收必选项。

页面交互

  • 搜索、添加、修改、删除、权益管理、支付网关权限管理：现网不变。
  • 保存商品后回到列表，新列立即反映最新配置与当前状态。

异常

  • 列表接口失败：现网错误提示；不得只缺新列却静默成功。
  • 前置商品名称拉取失败：前置条件列降级为「购买过 · {ID}」。

数据流转

列表接口在原有商品字段上增加限购、前置行为、前置商品 ID（及名称）、有效开始 / 结束；当前状态与 APP 可售判断规则一致。

V51-API-01

APP 可购商品过滤与下单校验

适用范围：向 APP 返回可购商品的接口（至少覆盖金币充值页所用列表），以及创建 / 支付该商品的下单接口。前端无改动。

功能逻辑

列表接口只返回「当前用户此刻可展示且可购买」的商品。用户买完限购商品或满足前置后，再次进入或刷新列表时，应看到集合变化（例如 A 消失、B 出现）。

下单接口必须再次校验，防止抓包或并发绕过列表过滤。

业务规则

1. 列表返回条件（须同时满足）

  • 产品状态为上架（或现网等价可售状态）。
  • 落在有效时间窗内（未配置时间窗则跳过本条）。
  • 若配置了前置条件：用户已满足该前置（本期即已购买过指定商品）。
  • 若配置了限购数 N≥1：用户对该商品支付成功次数 < N。
  • 现网其它过滤（如「可行类型」）继续生效，与本期能力取交集。
  • 排序：仍按商品「排序」字段及现网规则。

2. 下单校验

  • 创建订单前按与列表相同的规则校验；任一不满足则拒绝创建。
  • 达限购：文案「该商品已达购买上限」。
  • 前置不满足：文案「暂不可购买该商品」。
  • 未上架或不在有效期：文案「商品已下架或未在售卖时间」。
  • 前端不改：错误走现网通用失败展示；message 由接口返回。

3. 并发

  • 同一用户并发导致突破限购：超限请求必须失败，不得两笔都成功。

页面交互

  • APP 充值页无新控件、无新弹窗。
  • 用户可见变化仅来自列表数据变化。

异常

  • 列表接口失败：现网错误 / 空态；不得降级为返回未过滤全量商品。
  • 下单校验失败：不创建成功单；展示接口错误文案。
  • 支付中商品变为不可购：支付结果以现网订单状态机为准；本 PRD 不另开退款规则。列表侧结束后不再露出新单入口。

数据流转

APP 打开金币充值 → 请求商品列表 → 服务端按状态 / 时间 / 前置 / 限购 / 可行类型过滤 → 返回。下单 → 再次校验 → 现网支付与发货。

前置条件 × 限购 组合场景

以下两种组合须在评审与测试中覆盖。商品 A 为首购特惠，商品 B 配置前置「购买过 A」。

场景 A 限购 B 配置 用户未买 A 用户已买 A（成功 1 次）
阶梯替换（双十一主路径） 限购 1 前置购买过 A；限购 1 列表仅 A A 因限购消失；B 出现。再买 B 后 B 也消失
同时展示 不限购 前置购买过 A；B 可限购或不限 列表仅 A A 仍在；B 同时出现
  • 列表过滤与下单校验必须对当前商品完整生效或完整拒绝，禁止半执行。
  • B 未满足前置时：列表不返回 B，表现为「没有这张卡」，不是灰态可点。
